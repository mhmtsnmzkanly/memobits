# Memobits interface architecture plan

Status: historical architecture plan. Interface/extension behavior and the
associated launch work are implemented; consult the
[roadmap](../roadmap.md) and [decisions](decisions.md) for current scope and
remaining limits. Phase descriptions below explain the design and delivery
sequence and should not be read as uncompleted tasks where later checkpoints
record completion.

Implementation baseline `113ec09`. This plan records interface, core, host and type decisions made since that baseline. Box and broader reference support were outside its original scope. These are target contracts and proposals unless later checkpoints record delivery. [Feature inventory](feature-inventory.md#interfaces-extensions-generics-and-host-capabilities) · [Current language decisions](decisions.md) · [Repository verification rules](../../AGENTS.md)

This document describes compiler architecture and prior approvals. The [full launch manifest](launch-manifest.md#full-launch-manifest) records the completed implementation scope, and its [operator matrix](launch-manifest.md#operator-contract-matrix) records the bounded expansion beyond the Add pilot. Use the [roadmap](../roadmap.md) as the restart point.

## Approved contracts

- The portable core, host capability layer and user code share one Memobits interface, extension and generic model. **Host** is the term for the capability layer. Memobits programs execute as Wasm only. A host implementation may use any suitable language and any Wasm32 host is a candidate if it meets the required contracts. Select the host profile in `project.toml`. Keep the host contracts minimal. JavaScript integration crosses the Wasm import boundary. The first implementation is CLI-only. A second JS host is deferred and would supply imports without a JavaScript code-generation target.
- The minimal portable core is owned by the Rust compiler and split into focused areas such as array, list and operations. `Array` belongs in the core. `Bytes` is outside the target core. The shipped `Bytes<N>` alias still exists at this baseline. The proposal `array(T; N)`, its relationship to `Array<T, N>`, and legacy compatibility remain open. Migrate source spellings together once their replacements work. Core primitive semantics stay stable regardless of host. Exact module boundaries and the source/intrinsic division are implementation choices.
- A nominal type declaration can independently have an optional data body, `{}` for fields or `[]` for variants, and a trailing inherent `extend` block as sugar. Omitting one does not determine whether the other can appear. The sugar preserves nominal identity and inherent extension semantics. A bodyless nominal type is distinct from an explicit empty struct `{}`. Treating the two as constructor equivalents is rejected. Value and construction syntax for bodyless types remain open.
- The planned ordered tuple scope includes arguments and results, struct fields and enum payloads. Labels are syntax sugar over the same underlying tuple projections. When initializing with labels, supply every field and evaluate the written initializers once in source order. Label order cannot change tuple position order or initializer evaluation order.
- `T?` is the intended sole source spelling for optional types. It is feasible as a source spelling over the existing optional type machinery. Stage the type spelling first, then `None` and `Some` construction. Exact construction and insertion rules and legacy compatibility remain open. `(borrow T)?` means an optional borrow, while `borrow T?` means borrowing an optional value. This direction does not widen the admitted borrowed payload positions.
- The target text type is lowercase `string`. Its contents are valid contiguous UTF-8. A `char` is exactly one Unicode scalar value. String traversal visits scalars, and string length counts bytes. Implement character literals first. Literal delimiters, escaping and traversal APIs remain open. Migrate lowercase `string` with the other source spelling changes once replacements work. Defer representation optimizations and allocator experiments until the basic contracts are exercised.
- Interfaces specify `borrow`, `share` or owned receiver access. The approved borrowed form is `fn draw(borrow self)`. Only the receiver may be implicitly borrowed or shared. Owned receiver use follows normal move or primitive copy rules. Other arguments retain their current explicit access rules. `pub interface` follows module visibility.
- Anyone can extend any type or interface. Independent packages may declare overlapping extensions. Candidates come from local extensions, public extensions contributed by explicitly and directly imported modules, and the core. Direct symbol imports do not activate module extensions. Grouped `use graphics::{Color, Draw};` is approved and equivalent to `use graphics::Color;` and `use graphics::Draw;`. It activates no module extensions. Transitive imports and module loading do not activate extensions. There is no `use extend`. The existing `[prelude]` in `project.toml` supplies automatic name aliases and can load modules. See [manifest configuration](../../crates/memobits-project/src/lib.rs) and [resolver name handling](../../crates/memobits-resolve/src/names.rs). That does not establish extension activation. Keep prelude bindings and incidental module loads separate from explicit module-import edges. Exact module-import mechanics, grouped aliases and nesting, and discovery implementation remain open.
- Postfix `point.draw() of graphics::Draw` selects the interface for that call. Group a selected call before chaining, as in `(point.draw() of graphics::Draw).inspect()`. Remaining interface declaration and qualification grammar is open. Unqualified receiverless calls do not select extensions. After interface and applicability checks, multiple candidates at a call are ambiguous, including candidates for the same type and interface. Report the call and candidate declaration locations. Import order, locality, and core membership do not silently decide the winner.
- Generic constrained calls select evidence in the caller context at compile time first. Carry the selected extension identity through generic calls. A forwarding generic must pass the evidence it received instead of resolving the constraint again in its definition module. Nothing here fixes a runtime dictionary, monomorphization format, or public evidence ABI.
- User-defined `+` uses the selected `Add` implementation. The pilot takes an owned receiver and an owned operand of the same type and returns that type. Launch completion also requires bounded operator expansion and associated `Rhs`/`Output` on selected evidence. Primitive `u32 +` keeps its fixed checked behavior and assignment `=` stays built in. Do not generalize this decision to every operator or allow host capabilities or visible extensions to change primitive arithmetic.

## Type surface and remaining proposals

| Proposal | Intended direction and boundary |
| --- | --- |
| Bodyless nominal syntax | `type Example;` is a candidate spelling for an approved bodyless declaration. Bodyless types are distinct from explicit empty structs. Empty-struct construction equivalence is rejected. Decide value and construction syntax before enabling construction. An incomplete or forward declaration is a separate idea. |
| Trailing inherent extension syntax | `type … extend …` illustrates the approved declaration-site sugar. Recommend normalizing it to the same nominal declaration and inherent extension facts as the separate form. Do not give the sugar preferential lookup. Exact delimiters, visibility spelling and ordering are open. |
| Array spelling and transition | Evaluate `array(T; N)` as a source spelling over the core fixed-array shape. Keep current `Array<T, N>` and `Bytes<N>` on their existing paths until compatibility and migration are specified. Excluding Bytes from the target core does not decide when or how to remove its current alias. |
| Optional construction | Consider `None` and contextual implicit `Some`. Recommend defining the expected-type sites and explicit wrapping fallback before introducing insertion. Keep layout and legacy migration separate from the type spelling. The approved grouping distinguishes `(borrow T)?` from `borrow T?` without enabling new loan transport. |
| Anonymous `{}` structural records | Exact field names and types, identity independent of field order. Initializers are evaluated once in written order. Recommend canonicalizing shape/layout by field key separately from the initializer sequence. No width subtyping, implicit nominal conversion or public layout guarantee in the first slice. |
| Nominal `[]` enums and contextual variants | Existing named enums remain nominal, including when their variant lists match. Proposed contextual *uses* initially apply to unit variants with a unique expected enum. Keep qualified variants and current payload-enum support intact. Contextual payload variants are later work. Without a unique context, diagnose and require an explicit qualifier. |
| Contextual record literals and blocks | Consider recognizing explicit field starts in expression position, using expected shape for checking and keeping normal blocks and control-flow braces intact. Empty braces and conflicting parses need an explicit rule. `$` is a fallback marker candidate if contextual parsing cannot keep the distinction predictable. Its placement and grammar are open. |

## Operator surface audit

At baseline `113ec09`, [`lex`, `Parser::expr` and `Parser::statement`](../../crates/memobits-syntax/src/lib.rs) give the following boundary. Common gaps are candidates for decisions, not automatic Rust parity.

| Status | Concrete surface and checks |
| --- | --- |
| Existing | Tight to loose: call/index/field postfix, prefix `+`, `-`, `!`, multiplicative `*`/`/`/`%`, additive `+`/`-`, relational, equality, `&&`, `\|\|`. Current binary groups associate left. `=` and arithmetic compound assignments are statement forms. Retain checked arithmetic and short circuiting. |
| Shipped / bounded | After additive arithmetic, add shifts, bitwise AND, XOR and OR in that order before relational/equality and Boolean groups. Test `x + y << n` and `a & b == c`, left-to-right operands and `List<List<u32>>` type closers. Preserve the approved unsigned shift count/failure rules and method equivalents. Numeric `as` casts bind more tightly than multiplicative operators and less tightly than prefix/postfix operators. Wrapping methods have no accepted symbolic aliases. |
| Open, bitwise family | `~` or another integer complement form, bitwise and shift compound assignments such as `&=` and `<<=`, and signed shifts. Decide spellings, widths, overflow/count rules and whether compound writes read the old place before the RHS. Existing `!` syntax does not by itself approve integer complement. |
| Open, arithmetic and expression candidates | Exponentiation (`**` as a candidate), updates (`++`/`--`), ranges (`..`/`..=`), and optional coalescing or propagation (`??`/postfix `?`). Decide per candidate: precedence and associativity, supported types, result and side effects, bounds or failure, and ownership. A committed `T?` type spelling does not approve postfix expression propagation. Existing `if` expressions do not imply a ternary operator. |

### Audit disposition for the OP1 launch

The OP1 launch matrix admits only the named arithmetic, bitwise/shift,
comparison, compound, and unary-negation families. No additional operator is
activated by analogy with Rust or another language. In particular, integer
complement, exponentiation, increment/decrement, ranges, optional coalescing,
postfix propagation, and ternary syntax remain outside this launch. This is a
scope disposition, not a syntax or precedence decision for a later proposal.
The approved compound family is still an implementation requirement; its
exclusive-place receiver and once-only place capture need statement-level
analysis and lowering support before a nominal compound can be safely enabled.

## Import activation cases

Use a fixture where `graphics` exports `Color`, `Draw` and an applicable public extension, and also declares a private extension. These are planned tests. Use the final module-import syntax once it is decided.

| Case | Expected result |
| --- | --- |
| Import `graphics::Color` and `graphics::Draw` individually, then repeat with `use graphics::{Color, Draw};`. | Both variants resolve the same symbols and apply the same visibility checks. Neither activates the module extension. With no other applicable candidate, the receiver call reports a missing extension. |
| Supply `Color` or `Draw` through `[prelude]` in `project.toml`, with no explicit module import. | Existing alias resolution works even when it loads graphics. It does not activate the extension. |
| Explicitly import the graphics module alongside the symbol imports. | Its public extension can participate. Its private extension cannot. |
| Import a module that itself imports graphics. | A transitively loaded graphics module provides no candidate unless the caller also directly imports it as a module. |
| Directly import two modules with applicable public extensions for the same type and interface, or combine an imported extension with a matching local or core candidate. | The call is ambiguous with candidate declaration locations. Reversing import order cannot select a winner. |

## MVP, coordination and verification

Phases 0–3 are a pilot checkpoint. A direct receiver call, one flat interface and a compile-time forwarding case do not satisfy the launch. Phase 3B covers full generics, associated types and the required operator matrix. Phase 4 contains required bounded core and data/text slices selected by the manifest. Phase 5 is the CLI host profile; JS is deferred. Use local-module executable tests and separate synthetic package-identity tests until real package support exists. Do not describe those as cross-package linking. Box, broader references, associated-type generalization beyond the launch contract, dynamic evidence dispatch, general overloads, runtime plugin discovery, stable external ABI and optimization are outside the launch.

Use disjoint workers for parser extraction, resolver indexing design, fixture review and backend extraction only when their file lists do not overlap. Once AST changes are needed, serialize integration through syntax, resolution, analysis and the downstream exhaustive matches. One worker owns shared guide/status updates. One build orchestrator uses the warm workspace Cargo target directory or the existing warm override. Serialize Cargo builds/tests with `-j1`, run targeted suites first, and budget one workspace test pass per integrated milestone plus focused retries for identified failures. Put Wasm outputs under a temporary directory.

For a mechanical slice, run the existing focused crate tests, `cargo fmt --all -- --check` and `git diff --check`. For a language slice, add compile-pass/fail cases at the boundary and verify the [runnable guide](../../examples/guide/src/main.mb) from source and standalone Wasm before declaring the gate open. Targeted commands include `cargo test -j1 -p memobits-syntax`, `cargo test -j1 -p memobits-resolve`, `cargo test -j1 -p memobits-analysis`, `cargo test -j1 -p memobits-ir`, `cargo test -j1 -p memobits-ownership` and a filtered `cargo test -j1 -p memobits-cli --test cli`. Run only the suites relevant to the active slice, then `cargo test -j1 --workspace` at integration. Keep exact call-site/candidate spans, ownership failures, source/artifact outputs and absence of unrelated export changes as evidence.
